# .NET Dependency Catalog

Use the latest stable version compatible with the repository target framework unless this catalog pins a version. Do not select a prerelease. Preserve an established compatible package and ask before replacing a conflicting library or changing architecture.

## Baseline For New Deployable HTTP APIs

- **FluentValidation**: use for request/command validation and keep business invariants in the service/use case. For an MVC API that selects automatic validation, register validators with `AddValidatorsFromAssembly(...)`, add `FluentValidation.AspNetCore`, and call `AddFluentValidationAutoValidation()` at the API boundary. Registration alone does not execute validators. Do not inject/call `IValidator<T>` in every service or write a custom action filter when the official integration satisfies the repository contract. Automatic MVC validation is synchronous: do not use it for validators containing async rules; choose an explicit application pipeline for those.
- **OpenTelemetry + Grafana observability stack**: use this as the default optional observability pipeline, never a deployment or application availability prerequisite. Apply [deployment-config-standards availability rules](../../deployment-config-standards/SKILL.md#health-and-observability) for missing/invalid configuration and exporter failures. When enabled, export telemetry through OTLP to an OpenTelemetry Collector; send logs to Loki, traces to Tempo, and metrics to Prometheus, then query and dashboard them in Grafana. Configure `service.name`, service version, environment, endpoint, and sampling outside code. Instrument ASP.NET Core, `HttpClient`, and runtime; add EF Core instrumentation only when EF Core is used. Never capture bodies, tokens, claims, connection strings, or sensitive values.
- **ASP.NET Core Health Checks**: expose liveness/readiness for deployable backends. Add provider-specific health-check packages only when the selected dependency requires them and after the normal dependency gate. Do not report healthy before required dependencies and startup work are ready.
- **OpenAPI**: expose an OpenAPI document for HTTP APIs using the implementation supported by the target .NET version or established repository. Ask separately when an interactive UI or a package beyond the framework capability is required.
- **Problem Details**: use the ASP.NET Core built-in error service and global exception handling for new HTTP APIs. This is an error contract, not a success envelope.
- **Asp.Versioning.Mvc + Asp.Versioning.Mvc.ApiExplorer**: add the latest stable versions compatible with the target .NET version for confirmed versioned controller APIs and versioned OpenAPI discovery. Use explicit URL-segment versions and require a version; do not enable implicit default-version fallback. Do not add the superseded `Microsoft.AspNetCore.Mvc.Versioning` package for new code.
- **AutoMapper 16.x**: use AutoMapper as the default DTO/entity mapper, at no lower than patched `16.1.1`; prefer the latest compatible patched `16.x`. Confirm Community/commercial license eligibility and inject any key through `AUTOMAPPER_LICENSE_KEY`/secret configuration. Keep profiles out of controllers, prefer `ProjectTo` for EF DTO reads, and test configuration. Do not use vulnerable pre-license v14 as a no-license fallback.

These baseline choices are pre-approved for their exact activation condition. Report what was added. They do not authorize replacing an established public contract or incompatible package without confirmation.

## Conditional Packages

- **libphonenumber-csharp**: add the latest stable compatible version when accepting human-entered phone numbers. Parse with an explicit configured or domain-owned default region for national-format input, catch parse failures, and require `IsValidNumber`; do not use a hand-written regex as the authoritative validator. Keep its frequently updated numbering metadata current. Preserve the submitted representation unless normalization (for example E.164) is part of the confirmed contract.
- **Microsoft.Extensions.Http.Resilience**: add when the application makes outbound HTTP calls that need timeout, retry, circuit-breaker, or other transient-failure handling. Configure policy per operation and retry only safe/idempotent work. Do not use the deprecated `Microsoft.Extensions.Http.Polly` package.
- **MassTransit**: use the repository's pinned compatible version for cross-process integration events. This ASRS repository currently pins `MassTransit.RabbitMQ` 8.5.10 and `Pandatech.MassTransit.PostgresOutbox` 7.1.1 for PostgreSQL-backed outgoing delivery; preserve per-module DbContext isolation and at-least-once/idempotent consumer behavior. Confirm transport and durability strategy before introducing messaging to another repository.
- **MediatR**: add the latest stable version compatible with the target .NET version only for confirmed in-process events across boundaries that cannot directly share persistence, or for CQRS after the user confirms the application warrants it. Before adding MediatR `13.0.0` or later, confirm that the consuming organization/client qualifies for the official Community License or owns the required commercial license, and wire any license key through secret configuration. Do not silently downgrade to v12 to avoid the license gate. Publish in-process events after the source transaction commits and treat delivery as non-durable; use MassTransit plus an outbox when durable delivery is required.
- **Yarp.ReverseProxy**: add the latest stable version compatible with the target .NET version only for a confirmed self-hosted .NET API Gateway/BFF. Use it for application-level routing, transformations, auth policy, or client-specific aggregation; do not add it when Nginx/Kubernetes routing alone satisfies the requirement.
- **gRPC**: add the compatible official .NET gRPC packages only after a concrete internal synchronous-call requirement justifies strongly typed low-latency/streaming RPC. Do not add gRPC speculatively; prefer MassTransit for asynchronous cross-process events and ordinary resilient HTTP for simple synchronous calls.
- **Quartz.NET**: add the latest stable version compatible with the target .NET version only for confirmed recurring/scheduled jobs. Use an in-memory store only when one-instance non-critical schedule loss is acceptable; use a persistent store plus clustering for business-critical or multi-instance execution. Make jobs idempotent and choose material misfire behavior explicitly.
- **Distributed cache/Redis**: add only after a measured hot-read, shared ephemeral-state, distributed rate-limit, or other concrete requirement is confirmed. Ask for the exact provider/package. Do not use a distributed cache as source of truth or a distributed lock as a cross-service transaction mechanism.
- **Object storage provider client**: add only after the provider is confirmed. Prefer bounded streaming and client-direct presigned upload URLs; use multipart upload for large/resumable files and never expose long-lived credentials or public write access.
- **ASP.NET Core SignalR + `@microsoft/signalr`**: add only after the realtime activation and provider gates in `platform-capabilities.md` pass. Treat delivery as non-durable, resync authoritative state after reconnect, authorize hubs/methods, and ask for a scale-out provider/backplane when multiple instances are in scope. Do not add Redis automatically.
- **Elasticsearch**: add only after the search-engine activation and ownership gates in `platform-capabilities.md` pass. Then use Elasticsearch as the default provider and `Elastic.Clients.Elasticsearch` as the official .NET client at a version compatible with the cluster/.NET target. Keep one reusable client instance and use async APIs. Do not add Elasticsearch for ordinary indexed database filters/prefix search.
- **External secrets/configuration provider client**: add only after the hosting environment and provider are confirmed under `platform-capabilities.md`. Prefer platform-native workload/managed identity and built-in configuration integration. Do not add Azure, AWS, Google, Vault, or another provider speculatively.
- **EF Core and database provider**: add only when relational persistence is selected. Never default to PostgreSQL or any provider. In a new or ambiguous project, ask which database/provider to use before scaffolding persistence.

## Test Stack

- Use xUnit and Moq at the latest stable versions compatible with the target .NET version.
- Use `Microsoft.EntityFrameworkCore.InMemory` at the latest version compatible with the selected EF Core version only when the tested service/handler directly depends on DbContext and a lightweight non-relational fake can represent the behavior. Use Moq instead when the service depends on repository interfaces.
- Add required test companions such as `Microsoft.NET.Test.Sdk` and the xUnit runner without a separate question when the approved test stack is activated.
- Do not claim EF Core InMemory proves transactions, migrations, foreign keys, unique constraints, concurrency, provider SQL, or other relational behavior. Add a real-provider test suite only when the user explicitly requests it.
